# ВышКат

Консольное приложение учёта транспорта и вещей сервиса кикшеринга.
Транспорт попадает на баланс после техосмотра. Программа выводит количество
объектов, суммарный суточный расход энергии, технику для новичков и инвентарь.

## Запуск

Требуется .NET SDK 8. Первый запуск требует доступа к NuGet для загрузки зависимостей.

```bash
dotnet run --project CPO.csproj
```

Режим `1` демонстрирует работу программы, а именно приём исправного транспорта, отказ в приёмке изношенного
транспорта или транспорта без тормозов, добавление вещей и тд.

Режим `2` позволяет вводить пользователю самому транспорт, контролируя и валидируя при этом ввод.

Пункт `0` завершает ввод и показывает отчёты.

## Модель и правила

- `Vehicle` -> базовый класс транспорта, `Bike` и `Scooter` -> конкретные виды
- `Thing` -> базовый класс вещей, `Helmet` и `ChargingStation` -> конкретные виды
- `IInventoryItem`-> задаёт название и ID объекта на балансе
- `IEnergyConsumption`-> задаёт суточный расход энергии. Его реализуют самокат,
  зарядная станция и другой транспорт/вещи, которые требуют электроэнергии
- `IServiceCenter`->  задаёт контракт техосмотра. `ExpertiseServiceCenter` принимает
  транспорт с состоянием не ниже 70 и исправными тормозами. Я выбрал именно такой алгоритм отбора транспорта,
  а при необходимости его можно заменить другой реализацией `IServiceCenter`
- `Service` -> управляет балансом и отчётами. Зависимость техосмотра передаётся
  через конструктор, а в `Program.cs` её собирает DI-контейнер

Уровень для новичка (`BeginnerEase`) лежит в диапазоне 1–10. Значение от 6
позволяет выдавать транспорт новичкам
Состояние лежит в диапазоне 0–100
Энергия это конечное неотрицательное число

Конструкторы отклоняют неверные значения, пустые названия и ID. В названиях
и ID удаляются пробелы по краям. `Service` проверяет уникальность ID
среди всего принятого транспорта и вещей
Повтор номера вызывает `InvalidOperationException`, неверные аргументы
`ArgumentException` или его подклассы
Отказ техосмотра возвращает `false` и не резервирует ID. 
Отчёты возвращают новые списки, не раскрывая списки парка
Консоль отдельно проверяет ввод, чтобы пользователь мог исправить ошибку.

## SOLID и обязательные вопросы

- **SRP:** доменные классы отвечают за данные и их корректность,
  `ExpertiseServiceCenter` отвечает за решение техосмотра, `Service` за баланс и
  отчёты, `Program.cs` за ввод, вывод и сборку зависимостей
- **OCP:** новый потомок `Vehicle` автоматически участвует в приёмке,
  инвентаризации и выборе для новичков. Реализация `IEnergyConsumption`
  добавляет его расход в общий отчёт без изменения `Service`
- **LSP:** `Bike` и `Scooter` соблюдают общие ограничения `Vehicle` и одинаково
  принимаются сервисом. Потомки вещей соблюдают контракт `Thing`
- **ISP:** инвентаризация, расход энергии и техосмотр имеют отдельные небольшие
  интерфейсы. Шлем и велосипед не реализовывают расход энергии
- **DIP:** наиболее явно применён в `Service`, он зависит от `IServiceCenter`,
  а конкретная реализация выбирается при регистрации в DI-контейнере

**Сознательно ограниченный принцип:** 
В консольном меню OCP соблюдается не полностью, новые наследники `Vehicle` обрабатываются без изменения `Service`. Для нового типа нужно добавить пункт меню и создание объекта в `Program.cs`. Я сделал это нарочно, чтобы не усложнять логику и не создавать фабрику типов. Общая логика сервиса при этом остаётся пригодной для новых видов транспорта и вещей

**Расширение:** 
Новый вид транспорта, к примеру Электровелосипед может наследовать `Vehicle` и реализовать
`IEnergyConsumption`
Сотрудник это человек, поэтому не должен
наследовать `Vehicle` или `Thing`, для его учёта нужен отдельный модуль
Инвентаризируемую запчасть можно сделать потомком `Thing`
Учёт склада с количествами и перемещениями потребует отдельного сервиса

**Тесты и подмена зависимости:**
`ServiceTests.AddVehicle_AcceptsVehicleWhenDiStubApproves` и
`ServiceTests.AddVehicle_RejectsVehicleWhenDiStubRejects` регистрируют
`StubServiceCenter` как `IServiceCenter` и получают `Service` из DI-контейнера.
Stub задаёт решение независимо от состояния транспорта. Тесты проверяют
приём и отказ, вызов техосмотра и влияние решения на отчёты.

`ExpertiseServiceCenterTests` фиксирует реальные правила на границах 69/70 и
при неисправных тормозах. 
Тесты `ServiceTests.GetVehiclesForBeginners_UsesEaseThreshold` и
`DomainTests.IsForBeginners_UsesEaseThreshold` фиксируют границу уровня для новичков 5/6.

Код тестов: [ServiceTests.cs](Tests/ServiceTests.cs),
[DomainTests.cs](Tests/DomainTests.cs),
[ExpertiseServiceCenterTests.cs](Tests/ExpertiseServiceCenterTests.cs).

## Проверка и покрытие

```bash
dotnet build CPO.csproj
dotnet test Tests/CPO.Tests.csproj
dotnet test Tests/CPO.Tests.csproj --collect:"XPlat Code Coverage" --results-directory ./TestResults
```

Последняя команда создаёт `coverage.cobertura.xml` в подпапке `TestResults`.
Покрытие измеряется для всего приложения, включая консольную
точку входа, без исключения доменных классов, сервисов или `Program.cs`
При финальной проверке прошли все 46 тестовых случаев.
Покрытие строк всего приложения = 98,81%,
ветвей = 99,07%. Покрытие доменных классов и сервисов = 100%.

## Использование ИИ

Я использовал ИИ, как "ревьювера", для проверки покрытия тестов и схожести с условием. Также использовал ИИ в качестве браузера,
уточняя некоторые моменты по синтаксису. Основная логика и модули проекта реализовал самостоятельно, без использования ИИ
